# Compatibility Report

What `markdown-core` parses and `markdown-compose` renders, measured against CommonMark 0.31.2 and the GitHub Flavored Markdown 0.29-gfm extensions. Which dialect enables which extension is in [dialects.md](dialects.md).

## Supported

- CommonMark block structure per the spec's parsing strategy: paragraphs with lazy continuation lines, ATX and setext headings, thematic breaks, indented and fenced code blocks, block quotes, tight and loose lists, link reference definitions (also multi-line ones), and tabs with four-column stops
- CommonMark inline parsing per the spec's reference algorithm: emphasis and strong emphasis (flanking rules, rule of 3), code spans, inline and reference links and images with titles, autolinks, backslash escapes, entity and numeric character references, soft and hard breaks
- GFM tables (cmark-gfm table extension rules, with alignment), task list items, strikethrough and extended autolinks, where the dialect enables them
- display math blocks (`$$` / `\[`) and inline math (`$...$`, `\(...\)`) in `GfmMath`
- append-only streaming with immutable snapshots, a stable prefix, stable block ids and explicit dirty-region reporting; every streamed snapshot equals a one-shot parse of the same text
- linear-time parsing on pathological input (deep nesting, long tables and lists, nested brackets, unmatched backticks, `$`, `\(`, `[`)
- Compose rendering of every node kind: paragraphs, headings, quotes, ordered, bullet and task lists, fenced and indented code (with syntax highlighting), math (through `MathRenderer`), thematic breaks, tables and links (opened through `LocalUriHandler` by default)

## Partially Supported

- images: parsed in the core model; the renderer shows alt text unless the app passes an `imageContent` composable
- Compose tables size columns from content (preferred and minimum width), shrink the widest columns first, scroll horizontally when even the minimum widths do not fit, and apply left/center/right alignment; there is no GitHub-style chrome
- Compose rendering aims at correctness and stable block identity, not GitHub visual fidelity

## Explicitly Unsupported

- raw HTML blocks and inline HTML
- footnotes and other GFM extensions beyond tables, task lists, strikethrough and autolinks
- HTML sanitization and HTML export
- editing in the middle of the source

## Known Deviations

- GFM extended `www.` / URL autolinks are suppressed while a link bracket is open (as in cmark-gfm)
- inline nodes nested deeper than 32 levels stay literal text
- raw HTML is not parsed, so the examples that rely on HTML blocks, inline HTML or HTML comments render the tags as text
- a task marker alone on an item's line (`- [ ]`) is an empty task item, where cmark-gfm requires a space or tab after the marker
- task list rendering uses read-only checkbox UI rather than plain textual markers
- image rendering emits alt text unless the app supplies `imageContent`; no built-in image fetching pipeline exists
- link titles are parsed but not shown by the renderer

## Test Suites

All suites run in `./gradlew ciCheck` on the JVM, JS and Wasm, plus iOS simulator tests in the macOS CI job, unless noted.

- `SpecConformanceTest` runs every CommonMark 0.31.2 example and the cmark-gfm strikethrough, autolink and table extension examples through a test-only HTML renderer. The examples are vendored as Kotlin, generated by `markdown-core/scripts/generate_spec_examples.py`. Every section must pass in full except the documented exclusions, and the test fails when an excluded example starts passing.
- `StreamingDifferentialTest` streams a corpus in every dialect under several chunkings (single characters, token-sized chunks, random splits, interleaved empty chunks) and checks that each snapshot equals a one-shot parse of the same prefix, that the stable prefix never moves backward or changes its blocks, and that the delta matches the snapshots. `StreamingFuzzTest` (JVM only, too slow for browser test runners) runs the same check on seeded random documents and chunkings and shrinks failures.
- `InlineParserRegressionTest` checks that every streamed prefix of a paragraph inline-parses like a one-shot parse; `InlineCheckpointTest` covers resuming a growing paragraph.
- `BlockStructureRegressionTest`, `MathBlockParserTest`, `InlineMathParserTest`, `DialectExtensionTest` and `CompatibilityRegressionTest` pin AST shapes for block structure, math, dialect differences and curated cases.
- `BlockParserPerformanceTest`, `InlineParserPerformanceTest` and `StreamingPerformanceTest` (JVM) bound the time spent on pathological and long streamed input.
- `MarkdownUiTest` (JVM, `markdown-compose`) renders documents with the Compose UI test framework: semantics, links, tables, images, math, lazy lists, and that streaming recomposes only the touched block. `MarkdownStreamingCostTest` (JVM) counts the blocks composed per streamed append in both renderers and bounds the cost of `MarkdownState.append` on large documents.
